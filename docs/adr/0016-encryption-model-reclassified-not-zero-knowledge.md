# ADR 0016 — Reclassify the encryption model: application-level encryption at rest, not zero-knowledge

**Status:** Accepted (2026-09-22)
**Amends:** ADR 0001 (Full zero-knowledge encryption from day one), ADR 0013 (Session-ticket KMS handshake)
**Context doc:** `docs/SECURITY_REVIEW_RESPONSE_2026-09-18.md` §4 Slice S3, responding to `DPNR_Enterprise_Security_Review_2026-09-14.md` finding DPNR-02

## Context

ADR 0001 committed this project to "full zero-knowledge encryption from day one," on the premise that "the backend never holds a key capable of decrypting user content on its own." ADR 0013 built the session-ticket handshake to preserve that premise as narrowly as possible: the KMS CMK is asymmetric, the private key never leaves KMS, and the client wraps its own DEK client-side against the CMK's public key.

That premise does not hold once the DEK is actually *used*. `getSessionCrypto()` (`infra/cdk/lambda/lib/session-crypto.ts`) calls `kms:Decrypt` and receives the **plaintext DEK back in the calling Lambda's process memory** — that's what `kms:Decrypt` does; there is no KMS operation that decrypts user content without exposing the unwrapped key to the caller. Every interactive Lambda that needs to read or write a message (Companion, Decision Room, Mirror Room) does exactly this, and then — separately, unavoidably — passes the resulting plaintext conversation content to AWS Bedrock (`infra/cdk/lambda/companion/message.ts`) so Claude can generate a reply. A true zero-knowledge design, where the backend never has content in a form it can read, is structurally incompatible with server-side AI processing of that content — the model has to read it to respond to it. The same is true of the Daily Card / Weekly Recap composer Lambdas, which run on a schedule with no user present and therefore *cannot* rely on a live client-side decrypt step at all.

Meanwhile the product's own consent screen and privacy policy tell users the opposite: `Consent.points.aiProcessesContent` says content is "encrypted so we can't access it either," and `Privacy.sections.security` calls the design "end-to-end encryption" under which content is "never readable in plain form outside an authenticated session of yours." Both statements are false as implemented. This is the more serious problem — not that the architecture is bad (it isn't; see Decision below), but that users are being told a materially stronger privacy guarantee than the one actually operating, on a product that invites disclosure of intimate psychological content.

## Decision

**Reclassify the encryption model from "zero-knowledge/end-to-end" to "application-level encryption at rest with KMS-mediated, time-boxed key access," and correct all user-facing copy to match.** We are not redesigning the crypto architecture. The KMS-asymmetric-CMK / client-side-wrap / session-ticket mechanism built under ADR 0013 is a genuinely good design for what it actually is: content is encrypted at rest with AES-256-GCM under a per-user DEK that no static, long-lived server-side key can unwrap; the DEK is only ever recoverable for a bounded ticket window (`active_session` / `post_session`), server-side, via an auditable `kms:Decrypt` call scoped by IAM to the specific Lambdas that need it. That is meaningfully better than "the backend holds a permanent master key," and worth keeping and worth describing accurately. It is not, and cannot honestly be marketed as, a guarantee that DPNR itself cannot read the content — DPNR's own infrastructure decrypts it routinely, by design, to do the product's core job.

A true zero-knowledge redesign (server structurally incapable of ever obtaining plaintext) would require removing or restructuring every feature that depends on server-side model access to content — Companion, Decision Room, Mirror Room, Daily Card, Weekly Recap — which is nearly the entire product. That is a real, large, separate product decision this ADR does not make and is not authorized to make.

ADR 0001's other consequence — no backend password/recovery-code reset flow, unrecoverable data loss on losing both credentials — **stands unchanged**. That commitment was never actually about zero-knowledge marketing; it's a real property of not escrowing a recovery path, and remains true and worth keeping regardless of how the encryption model is described to users.

## Consequences

- `Consent.points.aiProcessesContent` and `Privacy.sections.security` are rewritten (this same change) to describe the actual model: encrypted at rest, per-user DEK, KMS-mediated and time-boxed access, decrypted server-side when needed to generate a reply or a scheduled summary — not "we can't access it," not "end-to-end."
- `Privacy.sections.dataSharing`'s Bedrock bullet drops the "no PII" claim — there is no PII detection or redaction step anywhere in the pipeline; the bullet should say what's actually sent (conversation content, for that request only) without a filtering claim this codebase doesn't implement.
- Same bullet's hosting claim ("Vercel") is corrected to match the actual deployment target (`apps/web/render.yaml` → Render) while this edit is already touching that sentence — an unrelated but adjacent drift (DPNR-15) not worth a separate pass.
- ADR 0001 remains **Accepted** for its recovery-code/unrecoverable-loss consequence, but its "zero-knowledge" framing is superseded by this ADR for anything touching AI-processed content specifically. Do not cite ADR 0001 alone as authority for privacy-copy language going forward — cite this ADR too.
- Future features that touch what the backend can read (a new AI feature, a new scheduled job, a new support/debug tool that reads decrypted content) should be checked against the copy this ADR establishes, not against the old "zero-knowledge" framing — if a new feature needs broader access than "the ticket window this user's own action opened," the privacy copy needs another pass, not a silent gap.
- This does not by itself close DPNR-02 as "resolved" — the report's recommendation to route the final copy through privacy counsel before external users see it still stands. This ADR makes the copy accurate to the current architecture; it does not substitute for that review.
